# 릴리즈 절차

## 왜 이 절차를 따르는가

- `main` 에 올라간 커밋은 Render 가 곧바로 운영 서버에 배포한다. 그래서 무엇이 나가는지 사용자가 먼저 보고 승인해야 한다.
  검증이 끝났다고 해서 알아서 합치지 않는다.
- 버전은 여러 곳(package.json, package-lock.json, 게임 안 새 소식, GitHub 릴리즈 본문)에 적힌다.
  하나라도 빠지면 화면의 버전과 릴리즈가 어긋난다. 어긋나면 `npm test` 가 실패하도록 해 두었으니, 실패 메시지를 따라 맞추면 된다.
- 릴리즈노트는 읽는 사람이 둘이다. 플레이어는 "나한테 뭐가 달라졌는지"만 알고 싶고, 개발하는 사람은 전부 알고 싶다. 그래서 두 벌을 쓴다.

## 한눈에 보는 흐름

1. 버전 번호를 정한다 (제안하고 사용자에게 확인받는다)
2. 최신 `main` 에서 `release/x.y.z` 브랜치를 만든다
3. 그 브랜치에서 작업하고 검증한다
4. 릴리즈 준비: 버전 올림 + 게임 안 새 소식 + GitHub 릴리즈 본문
5. PR 을 만든다 (`main` ← `release/x.y.z`)
6. **멈추고 승인을 기다린다**
7. 승인되면 머지한다 (사용자가 GitHub 에서 직접 머지해도 된다)
8. 태그와 GitHub 릴리즈가 만들어졌는지, 배포된 서버의 버전이 맞는지 확인한다

## 1. 버전 번호

`x.y.z` 형식이다.

| 자리 | 뜻 | 언제 올리나 |
| --- | --- | --- |
| 메이저 `x` | 큰 개편 (나중에 리더보드가 생기면 시즌으로 쓴다) | 사용자가 분명하게 승인했을 때만 |
| 마이너 `y` | 기능 묶음 | 새 모드, 새 화면, 사운드 같은 큰 추가 |
| 패치 `z` | 작은 추가·수정·버그 수정 | 그 밖에 |

번호는 제안만 하고, 사용자가 정한다. 작업을 시작할 때 미리 정해 두면 브랜치 이름을 바꿀 일이 없다.

통신 규격(`PROTOCOL_VERSION`, `src/shared/protocol.ts`)은 버전과 별개다. 서버와 화면이 주고받는 내용의 모양이나 뜻이 바뀔 때만 올린다.

## 2. 브랜치

```bash
git fetch origin main
git checkout -b release/x.y.z origin/main
```

한 버전에 들어갈 작업은 모두 이 브랜치에 커밋한다. `main` 에는 직접 커밋하거나 푸시하지 않는다.

## 3. 작업과 검증

저장소의 `CLAUDE.md` 에 있는 기준을 따른다. 요약하면: `npm run typecheck`, `npm test`, 화면이 바뀌었으면 실제 브라우저로 여러 화면 크기에서 확인.
확인하지 못한 것은 PR 본문에 그대로 적는다 (릴리즈노트에는 적지 않는다. 아래 4 (다) 참고).

## 4. 릴리즈 준비

작업이 끝났을 때 한 번에 한다 (작업 도중에 미리 올려 두면 다른 변경과 섞여 빠뜨리기 쉽다).

**(가) 버전 올리기** — package.json 과 package-lock.json 이 함께 바뀐다.

```bash
npm version x.y.z --no-git-tag-version
```

**(나) 게임 안 새 소식** — `src/shared/releases.ts` 의 `RELEASES` **맨 위**에 항목을 추가한다.
`date` 는 릴리즈를 준비한 날(PR 을 올리는 날)이다. 승인이 며칠 늦어져도 고치지 않는다.
화면 구석의 버전 표기도 이 값에서 나온다. 쓰는 법은 아래 "게임 안 새 소식 쓰는 법" 참고.
`.md` 파일만 바꾼 커밋은 배포를 일으키지 않게 설정되어 있으므로(`render.yaml` 의 `buildFilter`), 플레이어에게 보일 문구는 반드시 이 파일에 있어야 한다.

**(다) GitHub 릴리즈 본문** — `docs/releases/x.y.z.md` 를 새로 만든다. 첫 줄은 버전만 적은 제목 줄(`# vX.Y.Z`)이고, 나머지가 릴리즈 본문이 된다.
GitHub 릴리즈의 제목은 **버전만** 쓴다 (`v0.0.2`). "— 첫 버전" 같은 요약 문구를 붙이지 않는다: 무엇이 바뀌었는지는 본문에 적는다.
이전 버전의 파일을 복사해서 시작했다면 첫 줄의 버전부터 고친다 (테스트가 확인한다).

```markdown
# vX.Y.Z

## 달라진 점
- (플레이어가 체감하는 변화. 게임 안 새 소식과 같은 내용을 조금 더 자세히)

## 고친 것
- (버그 수정)

## 내부 변경
- (보안, 구조, 테스트, DB, 배포 설정 등. 무엇을 왜 바꿨는지)

## 확인한 것
- (테스트 수, 브라우저 검사 등 실제로 한 것)
```

해당하는 내용이 없는 절은 지운다.

**릴리즈노트에는 "확인하지 못한 것"을 적지 않는다.** 릴리즈노트는 사용자가 승인한 뒤에 나가는 글이고, 승인했다는 것은 사용자가 확인했다는 뜻이다.
이미 나간 버전의 기록에 "확인하지 못했다"는 말이 남으면 사실과 다르다.
확인하지 못한 것은 승인 **전에** 사용자가 알아야 하는 것이므로 PR 본문과 대화에서만 말한다 (아래 5 참고).
게임 안 새 소식에도 적지 않는다.
대신 한 것을 한 만큼만 적는다: "봇으로 혼자 하기를 쟀다"처럼 범위가 드러나게 쓰면, 하지 않은 것을 따로 늘어놓지 않아도 부풀린 말이 되지 않는다.

**(라) 확인**

```bash
npm run typecheck && npm test && npm run build
```

`npm test` 에는 버전이 모든 곳에서 같은지, 새 소식이 규칙(5줄 이하, 한 줄 70자 이하)에 맞는지, 릴리즈 본문 파일이 있는지,
릴리즈노트에 "확인하지 못한 것"이 들어가지 않았는지 확인하는 테스트가 들어 있다.
새 소식 화면이 실제로 어떻게 보이는지 브라우저로 한 번 열어 본다 (타이틀 화면 구석의 버전 표기를 누르면 열린다).

## 5. PR 만들기

클라우드 세션에서는 `gh pr create` 가 동작하지 않을 수 있다 (GraphQL 이 막혀 있다). REST 로 만든다.

```bash
git push -u origin release/x.y.z
gh api -X POST repos/{owner}/{repo}/pulls -f title='vX.Y.Z — 한 줄 요약' -f head='release/x.y.z' -f base='main' -F body=@/경로/pr-body.md
```

PR 제목에는 무엇이 들어가는지 알 수 있게 요약을 붙인다. (GitHub 릴리즈의 제목은 다르다: 버전만 쓴다.)

PR 본문에는 사용자가 승인 여부를 판단할 수 있는 것을 담는다.

```markdown
## 이번 버전에 들어가는 것
- (기능·수정 요약)

## 게임 안 새 소식 (플레이어에게 보이는 문구)
> 제목
> - 항목들 (releases.ts 에 적은 그대로)

## GitHub 릴리즈노트
docs/releases/x.y.z.md (머지하면 이 내용으로 릴리즈가 만들어진다)

## 검증
- (실행한 것과 결과)

## 확인하지 못한 것
- (있으면. 여기에만 적는다: 릴리즈노트와 새 소식에는 옮기지 않는다)
```

## 6. 승인 기다리기

PR 을 만들었으면 주소를 알리고 **멈춘다**. 다음 둘 중 하나가 승인이다.

- 사용자가 GitHub 에서 PR 을 직접 머지한다
- 사용자가 대화에서 승인한다 ("승인", "머지해줘" 등)

승인을 받은 뒤에 내용을 고쳤다면, 무엇을 고쳤는지 알리고 다시 승인을 받는다 (승인한 것과 다른 것이 나가면 안 된다).

## 7. 머지

사용자가 대화에서 승인했을 때만 직접 머지한다.

```bash
gh api -X PUT repos/{owner}/{repo}/pulls/{번호}/merge -f merge_method=merge
```

## 8. 머지한 뒤

- `.github/workflows/release.yml` 이 `main` 의 버전을 읽어 태그 `vX.Y.Z` 와 GitHub 릴리즈를 만든다 (제목은 버전만, 본문은 `docs/releases/x.y.z.md`).
  1~2분 뒤에 만들어졌는지 확인한다.

  ```bash
  gh api repos/{owner}/{repo}/releases/tags/vX.Y.Z --jq '.html_url'
  ```

- 만들어지지 않았으면 Actions 실행 기록을 보고 원인을 사용자에게 알린다.
  클라우드 세션에서는 GitHub 릴리즈를 만들거나, 고치거나, 지울 수 없다 (API 가 거부한다). 일부러 막아 둔 것이므로 다른 길로 돌아가려 하지 않는다.
  릴리즈를 직접 만들거나 고쳐야 할 때는 사용자에게 GitHub 화면에서 해 달라고 한다
  (Actions 탭에서 다시 실행하거나, Releases 화면에서 제목은 버전만, 본문은 `docs/releases/x.y.z.md` 에서 첫 줄을 뺀 나머지).

- 배포가 끝나면 서버의 `/healthz` 가 새 버전을 돌려준다 (`{"ok":true,"version":"x.y.z",...}`).
  클라우드 세션에서는 운영 사이트 접속이 막혀 있을 수 있다. 그때는 확인하지 못했다고 말하고, 사용자에게 타이틀 화면 구석의 버전을 봐 달라고 한다.

## 게임 안 새 소식 쓰는 법

그 버전을 처음 보는 모든 사람에게 한 번 자동으로 뜨는 글이다. 게임을 하러 온 사람을 잠깐 멈춰 세우는 것이므로, 읽을 가치가 있는 것만 짧게 쓴다.

**넣는 것**: 새로 할 수 있게 된 것, 눈에 보이게 달라진 것, 난이도·밸런스 변화, 플레이어가 겪던 버그를 고친 것.

**빼는 것**: 보안 내부, 코드 구조, 테스트, DB, 배포 설정, 성능 수치. 중요한 변경이어도 플레이어가 체감하지 못하면 GitHub 릴리즈 본문에만 적는다.

**문체**
- 한 줄에 하나, "~해요" 체, 한 줄 70자 이하, 한 버전에 5줄 이하
- 개발 용어를 쓰지 않는다 (스냅샷, 프로토콜, 서버 권위, 마이그레이션 같은 말)
- "무엇을 만들었는지"가 아니라 "플레이어에게 무엇이 달라졌는지"를 쓴다

**예시**

| 한 일 | 게임 안 새 소식 |
| --- | --- |
| 시야선이 막힌 적을 스냅샷에서 빼도록 변경 | 벽 너머의 적은 보이지 않아요. |
| 장전 동작 중 이동 속도를 70% 로 | 장전하는 동안에는 조금 느리게 걸어요. |
| 메시지 레이트리밋 추가 | (적지 않는다) |
| 난수를 예측할 수 없게 교체 | (적지 않는다) |

플레이어가 체감할 것이 하나도 없는 버전(내부 수정만)이라면 한 줄만 쓴다: "눈에 보이지 않는 곳을 다듬었어요."

## 자주 하는 실수

- `main` 에 직접 푸시하기: 승인 없이 운영에 나간다.
- 버전만 올리고 새 소식이나 릴리즈 본문을 빠뜨리기: `npm test` 가 알려 준다.
- 새 소식을 `RELEASES` 의 맨 위가 아닌 곳에 넣기: 화면의 버전이 바뀌지 않는다.
- 릴리즈 본문에 쓴 문장을 그대로 새 소식에 붙이기: 플레이어에게는 길고 어렵다.
- 릴리즈노트에 "확인하지 못한 것"을 적기: 승인받고 나가는 글이므로 적지 않는다. PR 본문에만 적는다 (`npm test` 가 알려 준다).
